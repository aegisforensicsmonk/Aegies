# Security Documentation

Because CIIP handles sensitive cyber investigation and digital forensics data, security and data integrity are prioritized at every layer of the application architecture.

## 1. Authentication & Authorization

- **JWT Authentication**: All API endpoints (excluding health checks and login) are secured using JSON Web Tokens. Passwords are never stored in plaintext; they are hashed using strong cryptographic algorithms before storage in the database.
- **Role-Based Access Control (RBAC)**: Enforced both globally (Admin vs. Investigator) and granularly (Case assignments). Access to specific evidence or cases is strictly compartmented based on user assignment.
- **Session Management**: JWT tokens include short expiration times. (Token refresh mechanisms are implemented to maintain active sessions securely without long-lived tokens).

## 2. Input Validation

- **Pydantic Models**: The FastAPI backend heavily utilizes Pydantic for request parsing and validation. All incoming payloads are strictly typed, ensuring that malformed or injection-style payloads are rejected with `422 Unprocessable Entity` before reaching business logic.
- **File Type Restrictions**: Evidence uploads are validated against a strict whitelist of allowed MIME types. This prevents the execution of malicious scripts disguised as evidence files.
- **CORS Configuration**: Cross-Origin Resource Sharing (CORS) is explicitly configured on the FastAPI middleware to only allow traffic from known frontend origins, mitigating CSRF attacks.

## 3. Data Protection & Forensic Integrity

- **Cryptographic Hashing**: Upon upload, the backend automatically computes a SHA-256 hash (and potentially MD5/SHA1) for every piece of evidence. This hash is stored and used to verify that the file has not been tampered with.
- **Immutable Chain of Custody**: The `chain_of_custody` table tracks every interaction with an evidence file. 
- **Database Immutability**: PostgreSQL triggers are employed on critical tables like `audit_logs` and `chain_of_custody` to physically reject `UPDATE` and `DELETE` SQL commands.
- **Soft Deletion**: Evidence and cases are never physically deleted from the database. The `is_deleted` flag is used to hide items from active views, ensuring that historical records are always recoverable for legal or audit purposes.

## 4. Error Handling

- **Sanitized Responses**: Custom exception handlers in FastAPI catch errors and return sanitized JSON responses. Stack traces and database structure details are never leaked to the client.
- **Secure Failures**: If authorization or validation fails at any point in a multi-step pipeline (e.g., during Celery task execution), the process fails securely without corrupting data state.

## 5. Security Best Practices

- **AI Advisories**: All output generated by the AI integrations (summaries, next steps) is clearly marked in the UI as advisory. This prevents users from blindly trusting non-deterministic outputs in legal contexts.
- **Environment Isolation**: Sensitive configuration (Database URLs, MinIO secrets, Secret Keys) is managed entirely via environment variables, ensuring secrets are not hardcoded into the repository.
- **Dependency Sandboxing**: The OSINT tools (osintfootprints) and Ransomware analysis modules operate in isolated containers, minimizing the risk of a compromised analysis tool affecting the core database or API.
